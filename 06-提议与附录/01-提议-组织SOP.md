# 1 提议：我们的组织SOP（WorkBuddy 版）

> **状态：提议，待讨论。** 地板（企微与 WorkBuddy 平台强制的必要流程）见 [[04-通用规则/02-红线速查-批了也没用别硬闯|通用规则：红线速查]] 与 [[03-企微bot维度/02-自建API机器人-原有三步流程照走|bot篇：自建API机器人]]；本篇是地板之上我们**自己设计**的管理动作——是否采纳、怎么调整，由管理层拍板。本篇由前库《01-提议-组织SOP》演化而来，管理对象从"机器人"扩展为"WorkBuddy 全形态"。

## 一、总原则

1. **谁要用谁申请、谁申请谁搭**：提需求的人就是搭场景的人（业务自助，DDD 客服团队已跑通）；
2. **审批只走一次**：上线前审一次，日常使用不逐次审批（授权是"第一次制"）；
3. **管理不拦路**：高频场景模板化免审、审批限时；管理动作服务业务，不卡业务；
4. **新增：账号归企微、资产进台账**：工作场景一律企微账号登录 WorkBuddy；场景资产（配置、提示词、连接器清单）全部进台账和公司 GitHub。

## 二、什么数据可以交给 AI（数据分级表）

分级表全文见 [[04-通用规则/03-数据分级-什么数据可以交给AI|通用规则：数据分级]]。要点：四级（公开/日常业务/敏感/绝密）；**聊天记录、邮件、会议纪要按内容就地升级**；敏感及以上数据不进个人账号、不进个人版。

## 三、场景从申请到上线，八步（前库七步 + 席位步）

```mermaid

    S2 --> S3["3 配置<br/>自建机器人走三步流程 或 WorkBuddy 官方形态直接配"]

    S4 --> S5["5 定数据放哪<br/>新数据进AI自建表 旧表只读挂索引"]
    S5 --> S6["6 试跑<br/>定时任务手动跑一次 通知通道实际收到一次"]
    S6 --> S7["7 上线检查<br/>清单逐项打勾"]

```

**发布审批的两个规矩**（平台机制实测，建议直接采纳，适用于自建机器人发布）：

1. **审批人必须选直属上级**：系统不会自动带出组织架构里的直属上级——不定规矩就会变成"挑个好说话的批"；
2. **申请原因写三要素**：做什么场景、动哪些表、读还是写。审批人只看这三样就能拍板。

## 四、别让审批变瓶颈

人人都想用 WorkBuddy，但席位要花钱、权限集中在管理员手里。四个办法：

1. **常用场景做成模板**：消息整理、定时简报、群内问答、台账登记这类高频场景预审成模板，模板内免逐个审；
2. **审批限时**：比如 2 个工作日，超时视为同意（限公开信息、日常业务两类低风险场景）；
3. **设 WorkBuddy 管理员**（见第七节）：席位分配、连接器审批交给业务侧专人；
4. **用量限额兜底**：管理端给每个场景设积分限额，超了自动停，不用逐个盯（见[[05-公司管理流程/06-用量与积分-额度加购限额三件事|管理流程：用量与积分]]）。

## 七、核心提议：设立 WorkBuddy 管理员

**现状**：企微超级管理员集中在 DIC IT 几个人；融合后审批需求从"偶发工单"变成"常态业务流"——每个用 WorkBuddy 的同事都要席位分配、连接器审批、用量限额，而"这个场景能不能用这份数据"本质是**业务判断**。

**提议**：

| 事项 | 提议 |
| :--- | :--- |
| 角色 | WorkBuddy 管理员（1-2 人，主管或专管） |
| 权限 | 企微管理后台 WorkBuddy 模块 + WorkBuddy 管理后台（建议**专用账号**，不挂个人） |
| 职责 | 席位分配、企业应用权限开关、连接器审批备案、用量限额、**操作留痕**、种子用户运营 |
| 边界 | DIC IT 保留企业认证、采购合同、组织架构、安全策略；日常 WorkBuddy 审批移交业务侧 |

**为什么值得做**：时效（不排 IT 工单队）、专业（业务判断归业务）、留痕（专人专号可审计，WorkBuddy 后台有操作日志）、减负（IT 回归运维本职）。

**风险与对策**：后台权限下放——专用账号 + 审批单留痕 + 定期权限审计；审批员不懂技术边界——以[[04-通用规则/02-红线速查-批了也没用别硬闯|通用规则：红线速查]]和[[04-通用规则/01-授权边界-敏感操作本人授权代发要确认|通用规则：授权边界]]为审批手册，首次上手由 DIC IT 带教；权责不清——与 DIC IT 书面划分边界，结论写回本篇第五节。
